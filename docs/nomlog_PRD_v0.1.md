## 1. 개요

### 1.1 한 줄 정의
먹은 음식을 가볍게 기록하고, 통계로 돌아보고, 소수의 친구와 나눠보는 개인 기록 앱.

### 1.2 배경 및 문제 정의
- 사람들은 이미 인스타 스토리, 셋로그 등으로 일상(특히 음식)을 습관적으로 기록/공유하고 있음. 하지만 이런 기록은 휘발되고 흩어져서, "내가 뭘 얼마나 자주 먹었는지" 되돌아볼 방법이 없음.
- 다이어트/칼로리 관리 앱(다이어트신, 인아웃, 밀리그램 등)은 이미 포화 시장이며 "관리·감량" 목적에 최적화되어 있음. 반면 본 프로젝트는 **관리가 아니라 재미·회고 중심의 기록**을 지향함 — 이 지점이 핵심 차별화.
- 예: "마라샹궈 1년에 한 번 먹는다"는 체감이 실제로는 어느 정도인지 기록으로 확인하고 싶다는 개인적 동기에서 출발.

### 1.3 목표 (이번 1개월 스프린트 기준)
- 만들 수 있는 가장 작은 형태로 핵심 루프(기록 → 통계 → 공유)를 완성한다.
- 지인 1~4명에게 실제로 써보게 하고, **계속 쓰고 싶은지 / 왜 안 쓰게 되는지** 데이터와 피드백을 얻는다.
- 사용자 확보와 무관하게, 기획–개발–배포–회고를 끝까지 완결한 결과물 자체를 포트폴리오 자산으로 남긴다.

### 1.4 목표가 아닌 것 (Non-goals, 이번 스프린트)
- 칼로리/영양소 계산, 다이어트 목적 기능
- AI 이미지 자동 인식
- 인스타/배달앱 연동
- 대규모 사용자 확보, 수익화
- 완성도 높은 디자인 시스템 (기능 검증이 우선)

## 2. 타겟 사용자

### 2.1 1차 타겟 (이번 스프린트)
- 준영의 지인 1~4명 (소그룹). 평소 인스타 스토리/셋로그 등으로 일상을 기록하는 습관이 있는 사람 우선.

### 2.2 향후 확장 타겟 (참고용, 이번 스프린트 범위 아님)
- 음식에 관심 많고 SNS에 기록을 남기는 습관이 있는 20대
- 맛집/다이어리 기록을 이미 하고 있으나 도구가 파편화된 사람

## 3. 경쟁 서비스 리서치 요약

> 상세 리서치는 대화 로그 참조. 핵심 인사이트만 정리.

| 서비스 | 카테고리 | 핵심 인사이트 |
|---|---|---|
| 셋로그 | 일상 기록(멀티미디어), 소셜 | 그룹 인원이 적으면(특히 2인) 한쪽이 이탈 시 같이 죽음. 뒤로가기·수정 반영 지연 등 사소한 UX 마찰이 반복적으로 불만으로 제기됨. 아이폰 전용으로 시작해 갤럭시 유저 배제로 인한 모임 참여 불가 불만 다수. |
| 다이어트신/인아웃/밀리그램/fatsecret | 식단·칼로리 관리 | "기록이 귀찮다"가 최대 공통 불만. 이를 줄이기 위해 업계 전반이 AI 사진 인식 방향으로 이동 중이나, 인식 정확도(양 추정, 오분류)는 여전히 한계. 그룹 공유·커뮤니티 기능이 리텐션 장치로 작동. |

### 3.1 시사점
1. **입력 마찰 최소화가 최우선 설계 원칙.** 기록 1건에 필요한 탭 수를 줄이는 것이 기능 추가보다 중요.
2. **소그룹 소셜은 구조적으로 취약.** MVP는 "혼자서도 완결되는 가치"(개인 기록·통계)를 먼저 확실히 하고, 소셜은 얹는 형태로 설계.
3. **차별화 지점은 "관리"가 아니라 "기록·재미·회고".** 경쟁군과 다른 포지셔닝을 기능 설계에서도 계속 지켜야 함.

## 4. 핵심 사용자 여정 (User Flow)

```
[음식을 먹음]
    ↓
[앱 열기] → [기록 추가: 이름 입력 + 카테고리 선택(선택) + 사진(선택)] → [저장, 1~2탭 이내]
    ↓
[기록 목록에서 확인] ←→ [이번 달/올해 통계 보기]
    ↓
[(선택) 기록을 이미지 카드로 만들어 공유]
```

**설계 원칙**: 기록 추가는 "생각 없이도 3초 안에 끝나는" 수준이어야 함. 리서치에서 확인된 최대 이탈 요인이 "입력 귀찮음"이기 때문.

## 5. 기능 명세 (Scope)

### 5.1 MVP 범위 (이번 1개월, Must Have)

| 기능 | 설명 | 우선순위 |
|---|---|---|
| 기록 추가 | 음식 이름(텍스트, 필수) / 카테고리(선택, 프리셋 or 자유입력) / 사진(선택) / 날짜·시간(자동) | P0 |
| 기록 목록 | 날짜별로 기록을 리스트/캘린더 형태로 확인 | P0 |
| 기록 수정·삭제 | 잘못 입력한 기록 정정 | P0 |
| 월간 통계 | 이번 달 기록 횟수, 카테고리별 빈도, 가장 자주 먹은 음식 Top N | P0 |
| 연간 통계 | 올해 누적 통계 (월간과 동일 로직, 기간만 확장) | P1 |
| 공유(이미지 카드) | 특정 기간 통계 또는 기록을 이미지로 내보내 카톡/인스타 공유 | P1 |
| 로그인 | 소그룹 테스트 수준의 간단한 인증 (소셜 로그인 1종 또는 이메일) | P0 |

### 5.2 의도적으로 제외 (Out of Scope, 확장 기능으로 유보)

| 기능 | 제외 사유 |
|---|---|
| AI 이미지 음식 인식 | 개발 비용 큼, 경쟁 서비스도 정확도 한계 있음. 검증 후 추가 검토 |
| 인스타/배달앱 연동 | 외부 API 의존성 큼, 1개월 내 무리 |
| 친구 추가 + 피드 소셜 | **오픈 퀘스천 (아래 6장 참조)**. 형태 미확정 상태로 무리하게 구현하지 않음 |
| 지역/연령대 비교 통계 | 사용자 수 확보 후에나 의미 있는 기능 |

## 6. 오픈 퀘스천 (아직 결정하지 않은 것)

이번 PRD에서 의도적으로 미확정 상태로 남겨두는 항목. 소그룹 테스트를 통해 답을 얻은 뒤 다음 스프린트에서 결정.

### 6.1 소셜 공유 방식
두 가지 방향을 검토 중이며, 아직 결정하지 않음:

- **A안 (피드형)**: 친구를 추가하면 서로의 기록을 타임라인/피드 형태로 자유롭게 열람. 셋로그보다는 인스타 피드에 가까운 느슨한 구조.
- **B안 (시간대 동기화형)**: 셋로그처럼 아침/점심/저녁 등 특정 시간대에 맞춰 그룹원들이 같은 타이밍에 기록을 공개. 긴장감과 동시성을 활용.

**결정 방법**: 1개월 MVP는 이 두 안에 공통으로 필요한 기반(개인 기록, 기록 데이터 구조)만 먼저 만들고 소셜 기능 자체는 착수하지 않는다. 지인 테스트에서 "다른 사람 기록이 궁금한지", "궁금하다면 어떤 방식이 자연스러운지"를 관찰/질문한 뒤 다음 스프린트에서 A/B 중 택일하거나 하이브리드로 설계.

### 6.2 백엔드/기술 스택
기획이 구체화된 지금 시점에 결정 예정 (본 PRD 승인 후 별도 기술 스택 문서에서 다룸). 후보:
- Spring Boot + PostgreSQL (DevSpace 재사용, 가장 익숙)
- Supabase/Firebase (개발 속도 우선)
- Kotlin/WebFlux (BMS 인턴 스택 연습 겸)

### 6.3 플랫폼 우선순위
모바일 앱 방향은 확정. 다만 iOS/Android 동시 대응 여부, 크로스플랫폼(Flutter 등) 채택 여부는 미정.

## 7. 성공 지표 (이번 스프린트 한정)

정량 지표를 크게 신뢰하기엔 테스트 인원(1~4명)이 너무 적으므로, **정성적 관찰 + 최소한의 정량 지표**를 함께 본다.

### 7.1 정량 (참고용, 절대 기준 아님)
- 테스트 참여자의 주간 평균 기록 횟수 (예: 주 3회 이상 기록하면 습관화 신호로 간주)
- 앱 설치 후 1주 리텐션 (재실행 여부)

### 7.2 정성 (더 중요)
- "기록하는 게 귀찮지 않았는가?" — 입력 마찰 관련 직접 피드백
- "왜 기록을 안 하게 됐는가?" (이탈 시) — 이유 파악이 다음 의사결정의 핵심 근거
- "다른 사람 기록이 궁금했는가?" — 6.1 오픈 퀘스천 해소용

### 7.3 Go/No-go 판단 기준 (1개월 후)
- **Go**: 테스트 참여자 다수가 스스로 기록을 이어가려는 의지를 보이거나, 명확한 개선 방향이 보임 → 다음 스프린트로 확장 개발
- **Pivot**: 기록 자체는 하지만 특정 마찰 지점 때문에 이탈 → 해당 지점 집중 개선 후 재테스트
- **No-go**: 대부분 며칠 내 흥미를 잃고 이유도 불명확 → 아이디어 자체를 재검토, 다른 아이디어로 전환 고려

| 소그룹 이탈 리스크 | 셋로그 사례처럼 1~4명 중 일부만 이탈해도 소셜 가치가 급격히 떨어짐 | MVP는 개인 기록만으로도 가치가 완결되도록 설계 (소셜은 부가 요소) |
